# Ozon inventory source contracts

M1 contract, checked 2026-11-06 against the [official Seller API reference](https://docs.ozon.ru/api/seller/), including its indexed reference through Context7 (`/websites/ozon_ru_api_seller`). This is a source-to-model contract, not an implemented HTTP client. No authenticated Ozon request was made for M1.

Use the endpoint reference, not tutorial snippets, as authority. The indexed documentation still contains older FBO list examples and inconsistent illustrative types. M6 must verify the selected versions, permissions, pagination and physical-event semantics against the connected account before enabling their adapters. Unsupported evidence below is deliberately incomplete, not permission to invent a date or quantity.

## Common contract

- Read requests use POST. Allowlist specific read endpoints; HTTP method alone does not establish safety. No marketplace writes or report-creation workflow is included here.
- Preserve int64 identifiers losslessly, then store identifiers as strings. Preserve leading zeros in articles/barcodes. Never substitute `sku` or `offer_id` into `product_id`, or derive a SKU from `OZN...` barcodes.
- Source identity is `(workspace, connection, domain, source ID)`. A source revision adds observation time, provider timestamps when supplied, sanitized facts, payload hash and adapter version. Event keys are stable across changed payloads; revisions do not create new physical events.
- Keep source product IDs, main/source/historical SKUs, articles and all barcodes separately. `role` describes a SKU observation; it does not create a separate SKU namespace. An absent ID or sentinel SKU `0` is unavailable for matching.
- Pagination must distinguish an empty successful result from missing fields or incomplete detail batches. Never advance completed coverage from a failed/partial traversal. Repeated cursors are failures, not successful completion. Do not expire bindings based on a partial response.
- Preserve every product line with a stable source-line identity. A line index in the synthetic fixtures is illustrative; M4 must establish endpoint-specific stable line keys and flag indistinguishable duplicates. Never use only `items[0]` or product name.
- Buyer/contact/address data and credentials are excluded from retained facts and fixtures. User-controlled catalogue metadata remains separate from source facts.

Response `items[].id` is product ID, `offer_id` is seller article, `sku` and `sources[].sku` are SKU facts. | Preserve `barcodes[]`, article, name, category/type, source SKUs and provider `updated_at`. Metadata observation and reviewed catalogue/mapping proposal only; no stock effect. Check requested IDs against returned details. |

It does not confirm an internal goods mapping. Preserve original field paths/types: the indexed illustrative `product_id: "door"` is not proof of a numeric catalogue ID. Unresolved/error entries remain unresolved. |
| Attributes: `/v4/product/info/attributes` | `last_id`, limit 1–1,000; response `result[]`, `last_id`, `total`. Product identity remains `id`; retain scalar `barcode` and `barcodes[]` without discarding either source. | Retain attributes and complex groups, ordered values and dictionary IDs. Names and values are evidence, not matching decisions. |

| Stock totals: `/v4/product/info/stocks` | Product/fulfillment identity and `last_id`; distinguish missing `stocks` from `stocks: []`. | `present`/`reserved` totals do not identify actual warehouses. Observation/reconciliation only; never create a movement or sum with warehouse analytics as additional stock. |
| Warehouse stock: `/v1/analytics/stocks` | SKU batches; preserve cluster and warehouse identity, required counts and response completeness. | Warehouse-level observation for cutover/reconciliation. Sale requires proven actual dispatch, positive whole quantities and all mappings. Confirm timestamp semantics per fulfillment flow in M6. |
| FBO postings: `/v3/posting/fbo/list` → `/v2/posting/fbo/get` | Posting number and all product lines; list offset/limit and documented terminal-page rule. M1's indexed documentation did not establish whether it means warehouse handover or buyer delivery. Do not enable automatic FBO Sale conversion until actual dispatch semantics are verified. Delivered status alone and processing time are insufficient. |
| FBO/FBS returns: `/v1/returns/list` | Return ID, posting number, SKU/article; `last_id` starts at numeric zero, subsequently follows last row ID while `has_next`; limit up to 500. Use one supported date filter per request. | Receipt requires actual physical receipt state, `product.quantity`, actual receiving place and receipt time. `logistic.final_moment`/`ReceivedBySeller` are candidates retained from the audit; verify their meaning for each return scheme. `target_place` alone is a planned destination. Initiation does not add stock. Partial/late receipts remain separate events linked to the original posting. |
| rFBS returns: `/v2/returns/rfbs/list` → `/v2/returns/rfbs/get` | List `last_id`/limit by return ID; detail unwraps `returns`, not `result`. | Current detail documentation exposes creation time, state, SKU/article and warehouse, but does not establish actual receipt quantity/time. Keep as evidence/incomplete proposal until supplied by a verified endpoint or reviewed user facts. Never substitute creation time or assume quantity one. |
| Own supplies: `/v3/supply-order/list` → `/v3/supply-order/get` → `/v1/supply-order/bundle` | List returns `order_ids` and `last_id`; request filter holds cursor/limit (1–100). Details accept up to 50 orders. Preserve each supply, destination and bundle separately. | Supply acceptance: `/v1/supply-order/act/product/get` | By `supply_id`; retain every act ID and item/SKU. | Distinguish `declared_quantity`, `fact_quantity`, `approved_quantity`, defects and unidentified quantity. Transfer needs actual quantity and both owned locations; disposal needs explicit completed disposal quantity/location/time. Creation or collection-ready status has no stock effect. |

## State and effect rules

- Before dispatch: cancellation has no inventory effect. After dispatch: cancellation does not restore stock; require physical return receipt or a reviewed correction.
- After a Sale, subsequent transportation/delivery observations update source status only. Do not issue another Sale or create available transit stock.
- Stock snapshots remain observations. Opening balances and later reconciliation are reviewed decisions under the cutover contract in M5.
- New source events require confirmed goods/location mappings before automatic acceptance. Changes to an accepted event require Review, retaining its original event identity and acceptance provenance.
- Same-name variants remain distinct unless explicitly mapped together. Unit/pack or identity-relevant variant changes invalidate automatic eligibility without changing the stable internal goods ID.
