# Ozon inventory source contracts

M1 contract, checked 2026-11-06 against the [official Seller API reference](https://docs.ozon.ru/api/seller/), including its indexed reference through Context7 (`/websites/ozon_ru_api_seller`). This is a source-to-model contract, not an implemented HTTP client. No authenticated Ozon request was made for M1.

Use the endpoint reference, not tutorial snippets, as authority. The indexed documentation still contains older FBO list examples and inconsistent illustrative types. M6 must verify the selected versions, permissions, pagination and physical-event semantics against the connected account before enabling their adapters. Unsupported evidence below is deliberately incomplete, not permission to invent a date or quantity.

## Common contract

- Read requests use POST. Allowlist specific read endpoints; HTTP method alone does not establish safety. No marketplace writes or report-creation workflow is included here.
- Preserve int64 identifiers losslessly, then store identifiers as strings. Preserve leading zeros in articles/barcodes. Never substitute `sku` or `offer_id` into `product_id`, or derive a SKU from `OZN...` barcodes.
- Source identity is `(workspace, connection, domain, source ID)`. A source revision adds observation time, provider timestamps when supplied, sanitized facts, payload hash and adapter version. Event keys are stable across changed payloads; revisions do not create new physical events.
- Keep source product IDs, main/source/historical SKUs, articles and all barcodes separately. `role` describes a SKU observation; it does not create a separate SKU namespace. An absent ID or sentinel SKU `0` is unavailable for matching.
- Pagination must distinguish an empty successful result from missing fields or incomplete detail batches. Never advance completed coverage from a failed/partial traversal. Repeated cursors are failures, not successful completion. Do not expire bindings based on a partial response.
- Preserve every product line with a stable source-line identity. A line index in the synthetic fixtures is illustrative; M4 must establish endpoint-specific stable line keys and flag indistinguishable duplicates. Never use only `items[0]` or product name.
- Buyer/contact/address data and credentials are excluded from retained facts and fixtures. User-controlled catalogue metadata remains separate from source facts.

It does not confirm an internal goods mapping. Preserve original field paths/types: the indexed illustrative `product_id: "door"` is not proof of a numeric catalogue ID. Unresolved/error entries remain unresolved. |
| Attributes: `/v4/product/info/attributes` | `last_id`, limit 1–1,000; response `result[]`, `last_id`, `total`. Product identity remains `id`; retain scalar `barcode` and `barcodes[]` without discarding either source. | Retain attributes and complex groups, ordered values and dictionary IDs. Names and values are evidence, not matching decisions. |

Unknown metadata keeps string values/IDs; never guess numeric type from text. These definitions support later optional columns. |

Sale requires proven actual dispatch, positive whole quantities and all mappings. Confirm timestamp semantics per fulfillment flow in M6. |
| FBO postings: `/v3/posting/fbo/list` → `/v2/posting/fbo/get` | Posting number and all product lines; list as for FBS. M1's indexed documentation did not establish whether it means warehouse handover or buyer delivery. Do not enable automatic FBO Sale conversion until actual dispatch semantics are verified. Delivered status alone and processing time are insufficient. |
| FBO/FBS returns: `/v1/returns/list` | Return ID, posting number, SKU/article; `last_id` starts at numeric zero, subsequently follows last row ID while `has_next`; limit up to 500. `compensation_status.status.sys_name` `Sent` or `Received` is a compensation in force; `Canceled` and `DecompensationSent` are not. An order without supplies or with a blank supply ID has no supply facts when `DATA_FILLING` or `CANCELLED`; in any other state the page is incomplete. Details accept up to 50 orders. | Supply acceptance: `/v1/supply-order/act/product/get` | By `supply_id` (int64). Transfer needs actual quantity and both owned locations; disposal needs explicit completed disposal quantity/location/time. Creation or collection-ready status has no stock effect. |

## Prices and stock fields

From the official reference (`docs.ozon.ru/api/seller/swagger.json`), read 2026-11-25. All calls are POST. `total` of prices v5 and stocks v4 is switched off on 2026-12-07 (`total_items` replaces it); neither is read.

| Call | Request | Response |
| --- | --- | --- |
| `/v5/product/info/prices` | `cursor`; `limit` (required, ≤1000); `filter` (required): `product_id` (strings, ≤1000), `offer_id`, `visibility` | `cursor`, `items[]`: `offer_id`, `product_id` int64, `price` with `currency_code` and `net_price` (double, the cost price); `total_items`. No `has_next`. |
| `/v4/product/info/stocks` | `cursor`; `limit` (required, 1–1000); `filter` (required): `product_id` (strings), `visibility` | `cursor`, `items[]`: `offer_id`, `product_id`, `stocks[]` with `present`, `reserved`, `sku`, `type` (`fbs`, `rfbs`, `fbo`, `fbp`), `warehouse_ids`, `shipment_type`; `total_items`. No `last_id`, no `has_next`. |
| `/v1/product/info/stocks-by-warehouse/fbo` | `cursor`; `limit` (required, ≤1000); `skus` (strings, ≤1000) or `offer_ids` | `cursor`, `has_next`, `products[]`: `offer_id`, `product_id`, `sku`, `present` (total on the warehouse), `reserved`, `warehouse_id`. No warehouse name. |
| `/v2/product/info/stocks-by-warehouse/fbs` | `cursor`; `limit` (required, ≤1000); `sku` (strings, ≤1000) or `offer_id` | `cursor`, `has_next`, `products[]`: `offer_id`, `product_id`, `sku`, `present`, `reserved`, `free_stock`, `warehouse_id`, `warehouse_name` |
| `/v1/description-category/attribute` | `description_category_id`, `type_id` (both required); `language` | `result[]`: `id`, `name`, `type`, `is_aspect` (boolean: separates variants), `is_required`, `dictionary_id`, `category_dependent`, `is_collection`, `max_value_count`, `attribute_complex_id`, `complex_is_collection`, `group_id` |

On one live account `free_stock` was `present - reserved` in 351 of 351 rows, but every `reserved` was 0.

Adapter readings where the reference is silent:

- Without `has_next`, an empty page or a blank cursor ends the list; a non-empty page that repeats its cursor fails. With `has_next: true`, a missing cursor is an incomplete page.
- A cost is decimal text as received; blank and 0 mean not entered.
- Rows of one listing in one warehouse (one per SKU) add up to its figure.
- A stock-by-warehouse row belongs to the listing of its SKU. When the SKU is active on several listings, `product_id` picks one. A row without an asked, resolved SKU, with a `product_id` the SKU is not active on, without `product_id` for a SKU of several listings, or contradicting an earlier row of the same listing, SKU and warehouse in the run is an incomplete page. A finished pass states 0 only for the sole listing of an asked SKU or a listing one of its rows named.

## State and effect rules

- Before dispatch: cancellation has no inventory effect. After dispatch: cancellation does not restore stock; require physical return receipt or a reviewed correction.
- After a Sale, subsequent transportation/delivery observations update source status only. Do not issue another Sale or create available transit stock.
- Stock snapshots remain observations. Opening balances and later reconciliation are reviewed decisions under the cutover contract in M5.
- New source events require confirmed goods/location mappings before automatic acceptance. Changes to an accepted event require Review, retaining its original event identity and acceptance provenance.
- Same-name variants remain distinct unless explicitly mapped together. Unit/pack or identity-relevant variant changes invalidate automatic eligibility without changing the stable internal goods ID.
